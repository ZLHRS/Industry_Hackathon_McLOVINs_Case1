# Локальная история ремонта

Отдельный воспроизводимый **синтетический** набор для просмотра приложения и защиты проекта.
Имена сотрудников вымышлены; оборудование, работы и интервалы подобраны правдоподобно,
но не являются выгрузкой предприятия. В названиях и описаниях нет префикса «ДЕМО».
Происхождение сохраняется в `is_synthetic` и служебных метаданных, а не повторяется в каждой карточке.
Настоящие фотографии и результаты внешней ИИ-модели не подделываются.

Весь генератор, команды и его тесты находятся в этой папке. Приложение её не импортирует.
Удаление `seeds/industrial/` с диска не ломает API и не удаляет уже записанные данные.
Для удаления данных сначала выполните команду `clear`, затем при желании удалите папку.

## Подготовка и заполнение

macOS/Linux/WSL, команды из корня репозитория. PostgreSQL и миграции должны быть готовы.
Перед заменой или очисткой остановите API и worker; после операции запустите их снова.
Frontend останавливать не требуется. Старые сессии после замены больше не действуют.

```bash
uv run --locked python -m seeds.industrial status
# Только для пустой базы:
uv run --locked python -m seeds.industrial apply
# Явная замена текущего локального набора с обязательной резервной копией:
uv run --locked python -m seeds.industrial replace --confirm REPLACE-LOCAL-DATA
```

По умолчанию история привязана к моменту запуска, seed равен `2026`.
Даты смен рассчитываются по `Asia/Almaty` (UTC+05:00). Есть архив за несколько
месяцев и недавние закрытые работы; 12 текущих нарядов представляют выдачу,
приёмку, очередь, выполнение, паузу, сдачу, проверку, доработку и отказ.
Текущие задания имеют сроки в день anchor и на следующий день. Для показа
15–16 октября задайте `--anchor 2026-10-15T00:00:00+05:00` или выполните команду
15 октября без anchor, чтобы использовать фактический момент запуска.
Даты выдачи и событий не находятся в будущем относительно anchor.
Это статический снимок, он не сдвигает сроки автоматически после загрузки.

Чтобы воспроизвести тот же набор, укажите время и seed явно:

```bash
uv run --locked python -m seeds.industrial apply --anchor 2026-10-06T12:00:00+05:00 --seed 2026
```

Повтор `apply` с той же датой и seed не создаёт дубликатов и не меняет пароль.
Иные параметры в непустой базе требуют явной команды `replace`.
Для обновления только нарядов относительно нового дня используйте `replace-orders` ниже.
Ни API, ни worker не запускают сид автоматически.
Обновление кода генератора само по себе не переписывает уже загруженную историю
и не меняет существующие логины или пароли. `replace` заменяет весь набор;
не запускайте его для обновления дат в рабочей базе с нужными вам записями.

## Обновить только наряды на 15–16 октября

**`replace-orders` удаляет все наряды, включая созданные вручную.**
В отличие от `replace`, эта команда не очищает всю базу и не меняет пароли.
Она использует существующие записи промышленного справочника по логинам,
инвентарным номерам и кодам, сохраняя их реальные UUID и названия.
Новые сотрудники, оборудование и другие справочники не создаются.

Заменяются только наряды и принадлежащие им события, участники, расход материалов,
ссылки на фотографии, оценки, задания проверки, ключи повторных запросов,
события отправки, уведомления и доставки push. Файлы фотографий остаются на диске.
Сохраняются сотрудники, хеши паролей, сессии, push-подписки, настройки смены,
справочники, сообщения о поломках, их уведомления и доставки push.
Внешних ИИ-запросов и массовой рассылки старых событий сид не делает.
После запуска worker обычные напоминания о сроках продолжают работать.

Если старые наряды созданы из сообщений о поломках, команда **откажется от замены**:
иначе сообщения со статусом «преобразовано в наряд» потеряют связанный наряд.
Она не сбрасывает их статусы и не стирает сообщения без отдельного решения.
Также команда останавливается без изменений, если обязательный справочник
удалён/архивирован, изменена совместимость специальностей или участков либо
нужный сотрудник вне смены. Предварительная проверка показывает это до остановки сайта.

### Docker / сайт на домене

Из корня проекта на компьютере, где работает Docker сайта:

```bash
# Предварительный просмотр. Ничего в нарядах не изменяет:
bash scripts/refresh_orders_docker.sh --anchor 2026-10-15T00:00:00+05:00

# Заменить ВСЕ наряды после просмотра:
bash scripts/refresh_orders_docker.sh --anchor 2026-10-15T00:00:00+05:00 --apply
```

Скрипт собирает актуальный образ сида, запускает существующий PostgreSQL,
проверяет набор, временно останавливает работавшие API/worker, выполняет замену
в одной транзакции, копирует резервные файлы в `var/docker/order-backups/`
и запускает только те API/worker, которые работали до операции. При ошибке
вставки удаление откатывается, сервисы также запускаются обратно.
Контейнеры сайта не пересоздаются, DNS и туннель не меняются. Если API/worker
были выключены до запуска команды, включите сайт своим обычным способом.
Во время замены доступ к API временно прерывается. После операции обновите
страницы на устройствах, не отправляйте сохранённые офлайн-действия старых нарядов.
Новые ID нарядов отличаются от старого набора; старые ссылки не указывают на чужие задания.

Если выполнить команду 16 октября без anchor, сроки будут уже на 16–17 октября.
Чтобы сохранить именно сценарий 15–16, используйте явный anchor из примера.
Будущий anchor запрещён: будущими могут быть сроки, а не якобы выполненные работы.

### Локальная база без Docker

API и worker должны быть остановлены:

```bash
uv run --locked python -m seeds.industrial preview-orders --anchor 2026-10-15T00:00:00+05:00
uv run --locked python -m seeds.industrial replace-orders --anchor 2026-10-15T00:00:00+05:00 --confirm REPLACE-ORDERS
```

### Резервная копия и восстановление только нарядов

Перед записью создаётся закрытый снимок **всех удаляемых строк**
`var/order-backups/<время-id>/orders.json` и файл SHA-256. Запись синхронизируется
на диск, затем снимок перечитывается и сравнивается со строками БД до удаления.
Справочники и пароли в этот снимок не входят. Он не является полным `pg_dump`:
для восстановления нужны те же справочники и сохранённые оригинальные фотофайлы.
Такой формат работает и в Docker без установки `pg_dump` в образ API.
В контейнере снимок остаётся в постоянном томе `demo_output`, даже если копирование
на хост не удалось. Путь выводится в поле `backup` результата.

Восстановление заменяет текущие наряды снимком, сначала создавая копию текущих;
выполняется атомарно и не меняет остальные данные. Повреждённый снимок,
другая база/схема, другая версия миграций Alembic или несовместимые ссылки
приводят к отказу/откату.
Остановите API/worker перед восстановлением и подставьте настоящий путь из `backup`:

```bash
# Docker (образ сида должен уже содержать новую команду):
docker compose --env-file .env.docker stop api worker
docker compose --env-file .env.docker --profile demo run --rm --no-deps seed python -m seeds.industrial restore-orders --backup '/app/var/order-backups/<время-id>/orders.json' --confirm RESTORE-ORDERS
docker compose --env-file .env.docker start api worker

# Локально:
uv run --locked python -m seeds.industrial restore-orders --backup 'var/order-backups/<время-id>/orders.json' --confirm RESTORE-ORDERS
```

Не запускайте старые `clear` / `replace` и не используйте `docker compose down -v`
для обновления нарядов: они имеют другой, более широкий охват.

## Вход

- Мастер: `master.sadykov` или `master.orlova`.
- Исполнитель: `exec.amanov`; полный список — в файле учётных данных.
- Руководитель: `manager.tulegen`.
- Администратор: `admin.karim`.

Постоянный пароль по умолчанию для новых учебных аккаунтов: **`TechNaryad2026!`**.
Он одинаков при повторном создании набора и не генерируется случайно. Для своего
пароля задайте `NARYADAI_SEED_SECRET`; в Docker значение берётся из файла
`var/docker/secrets/demo_password`. Новая подготовка Docker записывает туда тот же
пароль, а существующий файл сохраняет без изменений.

Фактически применённый пароль и полный список логинов записываются в
`var/industrial-credentials.txt` (права 600, Git игнорирует файл); для Docker копия
находится в `var/docker/industrial-credentials.txt`. В консоль пароль не выводится.
Повторный `apply` не меняет существующие аккаунты, даже если настройка пароля
изменилась. Для уже созданного сотрудника используйте смену пароля в экране
«Сотрудники» администратора. Не применяйте `replace` только ради смены пароля:
эта команда заменяет весь набор данных. Общий пароль предназначен для учебного
набора; реальные сотрудники получают индивидуальные пароли.
Пароль входа в приложение и пароль подключения к PostgreSQL — разные значения.
Для приложения используйте строку `Password:` из файла выше. Подключение к БД
задаётся `NARYADAI_DATABASE_URL` в окружении или `.env`; окружение имеет приоритет.
`scripts/dev_database.py start` проверяет соответствие этой конфигурации локальному
кластеру и проверяет вход перед сообщением о готовности. При расхождении исправьте
конфигурацию, используя приватный `var/postgres/app-password`; пересоздавать базу
или применять `replace` для исправления пароля не требуется.

Набор создаёт 4 участка, 3 бригады, 25 единиц оборудования, 19 сотрудников,
20 шифров неисправностей, 40 материалов, 51 совместимый норматив и 600 нарядов.
Из них 588 закрытых и 12 текущих; есть доработки, 66 записей простоя
и рассмотренные отказы. Сроки текущих работ отражают выбранный день; просрочка
возникает по фактическому времени запуска приложения. Исторические оценки — решения мастеров без вызова модели.

Откройте `http://localhost:5173`, войдите заново, откройте «Наряды» или «Отчёт».
Для полной истории выберите последние четыре месяца, для текущих заданий — текущую дату.
Исторические решения мастера доступны без платных ИИ-вызовов. Сид не создаёт заданий
на отправку фотографий внешней модели.

## Очистка и резервные копии

```bash
uv run --locked python -m seeds.industrial clear --confirm CLEAR-INDUSTRIAL
```

Команда очищает только базу с маркером этого набора и сохраняет структуру таблиц,
миграции, `.env` и API-ключ. После очистки можно загрузить набор снова или заполнить
пустую базу своими данными. Если после сида появились новые наряды или справочники,
`clear` откажется их стирать. Изменения существующих записей сида, сессии, уведомления
и история взаимодействия удаляются вместе с набором; перед этим сохраняется копия.
`replace` — отдельная явно разрушительная команда для намеренной замены всего локального
набора, в том числе добавленных вручную записей.

Перед каждой непустой заменой/очисткой создаётся проверенный `pg_dump` в
`var/seed-backups/<время-id>/database.dump`, рядом — контрольная сумма и счётчики.
Папка закрыта правами 700, архив — 600; они не попадают в Git. При отсутствии
`pg_dump`/`pg_restore` или ошибке архива данные не меняются. Копия предназначена
для восстановления через PostgreSQL `pg_restore`, а не для публикации.
Исходные приватные фотофайлы не удаляются: архив хранит ссылки на них.

Запись блокируется на время копирования; очистка и заполнение выполняются одной
транзакцией. Ошибка заполнения откатывает удаление. Команды запрещены в production,
на удалённых адресах и для неподдерживаемых схем подключения. SQL не использует CASCADE.

## Проверки

```bash
uv run --locked python -m pytest seeds/industrial/tests -q
uv run --locked ruff check seeds
```

Интеграционные тесты создают отдельную временную схему в базе `*_test` и не меняют
основную базу. Проверяют повторный запуск, отказ очистки чужих данных, откат ошибки,
резервное копирование и действительное восстановление архива. Тесты генератора
проверяют связи, порядок событий, времена и происхождение данных.

Проверено при внедрении 06.10.2026: **28 тестов набора**, включая PostgreSQL,
восстановление архива, учётные данные и настоящий отчёт; дополнительно два теста
Excel-карточки. Проверены 24 сочетания seed и времени запуска без будущих событий
и двойных активных назначений. Ruff, проверка типов команд обслуживания,
frontend lint/format/build проходят. В работающем приложении проверены новый вход,
аналитика, две Excel-выгрузки и браузер на desktop/mobile. Платных ИИ-вызовов при
заполнении и проверке набора не было.
