# Этап 2: PostgreSQL, авторизация и демонстрационные данные

Проверено в Ubuntu/WSL, Python 3.13.13, PostgreSQL 16.15. Дата: 5 октября 2026.
Граница этапа — работающий backend данных и доступа. Сквозной ремонт через HTTP/UI ещё не готов.

## Результат

- 16 таблиц приложения, начальная миграция Alembic, ограничения ссылок/диапазонов/времени.
- Асинхронная SQLAlchemy, ограниченный пул и таймауты, корректное закрытие соединений.
- POST login/logout, GET me, Argon2id, случайные сессии с хранением только SHA-256 отпечатка.
- Лимиты по логину и TCP-адресу в БД; ограничения выдерживают конкуренцию и рестарт API.
- Администратор создаёт/редактирует справочники и учётки; изменение доступа отзывает сессии.
- Области доступа фильтруют участки, оборудование и сотрудников; чужое оборудование даёт 404.
- Readiness проверяет доступность БД и revision; миграции не выполняются при старте API.
- Локальный проектный PostgreSQL без sudo; отдельная роль приложения без superuser.
- Инструкция запуска, CI с обязательной PostgreSQL и реестр компонентов обновлены.

## Проверки

Команды приведены в README. Все интеграционные тесты работают с настоящим PostgreSQL,
в отдельных случайных схемах внутри `naryadai_test`, без SQLite.

- Unit/API/integration: **141 тест**, без пропусков; покрытие с учётом ветвей — **96,74%**.
- Ruff, форматирование, strict mypy и актуальность lockfile: **PASS** на всём проекте.
- Alembic metadata parity и upgrade → downgrade → upgrade: проверены.
- Ограничения FK, соответствие оборудования участку и хронология: проверены на уровне БД.
- Сессии: неправильный секрет/токен, истечение срока, блокировка сотрудника, отзыв и смена секрета.
- Конкурентные входы: лимит не расходуется дважды; лимиты сохраняются между API-инстанциями.
- Доступ: 401/403/404, admin-only записи, откат транзакции при неверной внешней ссылке.
- Seed: детерминизм, минимумы, история, отсутствие пересечений завершённых работ,
  четыре контрольных паттерна, повтор без дублей, CLI и чтение данных через API.
- Настоящий HTTP/Uvicorn: live/ready, вход и справочники четырёх ролей, logout и 401 после него.

Coverage учитывает ветви, worker threads и greenlet-мост SQLAlchemy:
[настройка concurrency в официальной документации Coverage](https://coverage.readthedocs.io/en/latest/config.html#run-concurrency).
