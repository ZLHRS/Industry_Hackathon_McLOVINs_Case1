# Этап 5: realtime, уведомления и контроль сроков

## Что реализовано

Архитектура остаётся модульным монолитом: HTTP API и отдельный worker используют одну
PostgreSQL. Миграция 0003_notifications добавляет журнал уведомлений, пользовательские
ревизии, подписки и очередь Web Push; прежние наряды, события и материалы сохраняются.

Транзакционный outbox создаётся вместе с изменением наряда. Worker сохраняет уведомления,
обновляет ревизии пользователей и только затем отмечает событие обработанным. SKIP LOCKED
позволяет запускать несколько workers. Realtime распространяется всем текущим наблюдателям
участка и прежнему исполнителю при переназначении; HTTP повторно проверяет права.

WebSocket /api/v1/realtime принимает Bearer-токен первым JSON-кадром:
{"type":"authenticate","token":"…"}; query-параметры запрещены. Проверяются Origin, сессия
и роль. Ревизии и heartbeat не содержат карточек, персональных данных или токенов.
Лимиты: 100 соединений на процесс, 4 на сотрудника, 5 секунд на авторизацию.
Клиент восстанавливает соединение с задержкой и перечитывает данные после ready.
Открытая карточка обновляется без сброса введённых полей.

## Политика сроков

| Событие | По умолчанию | Результат |
| --- | --- | --- |
| Приближение срока | За 30 минут | Напоминание исполнителю |
| Непринятый обычный наряд | Через 10 минут | Эскалация мастеру |
| Непринятый аварийный наряд | Через 3 минуты | Эскалация мастеру |
| Просрочка | С наступления срока | Исполнитель и выдавший мастер |
| Повтор просрочки | Каждые 30 минут | Оба адресата, по одному сообщению в интервал |
| Длительная просрочка | Через 60 минут | Руководители соответствующего участка |

Настройки находятся в .env.example. Все часы серверные, timezone-aware UTC.
Сканирование использует переданное время для воспроизводимых тестов.
Дедупликация привязана к наряду, попытке, сроку и интервалу, для непринятия — также
к последнему переназначению. Перезапуск не создаёт повтор в том же интервале.
Закрытые, отменённые, отклонённые и переданные на проверку наряды не получают таймерных напоминаний.

Просрочка содержит номер, оборудование, участок, исполнителя, статус, задержку и комментарий.
Рекомендация замены учитывает участок, смену, активность, специальность, разряд и отсутствие
текущей работы. Это предложение мастеру; автоматического переназначения нет.
Окончательный допуск повторно проверяется обычной командой назначения.

## Журнал и Web Push

Журнал персональный, с пагинацией, фильтром непрочитанных, прочтением и отдельным
подтверждением получения аварийного сообщения. Подтверждение не принимает наряд.
После смены назначения/доступа чужой журнал и карточка недоступны даже по сохранённому ID.
Ссылка из push открывает доступную карточку через авторизованный API.

Push-подписка привязана к аккаунту и сессии. После входа регистрация обновляется;
выход отзывает сессию и пытается удалить подписку. Worker повторно проверяет сессию,
активность, участок и текущее назначение перед отправкой. Экран блокировки получает
общий текст без производственных подробностей.

Сетевая доставка выполняется вне транзакции и отдельно от проверки сроков. Используются
сохраняемые leases, лимит параллелизма и повторов. Ответы 404/410 отключают подписку;
429/5xx/сетевые ошибки повторяются с задержкой. Ответ push-провайдера означает принятие
запроса, а не доказательство показа пользователю. После сбоя между отправкой и записью
результата возможен повтор; устойчивый notification tag объединяет такой показ.

Разрешены HTTPS endpoints FCM, Mozilla, Apple и WNS. Ввод ключей валидируется;
redirects и proxy из окружения отключены. Приватный VAPID-ключ остаётся в игнорируемом var/
с правами 0600; в репозиторий и клиент передаётся только открытый ключ. Контакт владельца
задаётся URI, helper может получить его из GitHub origin без передачи credentials.

Service worker кеширует только публичную оболочку. API, фото и токены не кешируются.
Нативный push обрабатывается отдельным событием; аварийное сообщение просит явного
взаимодействия и вибрации там, где браузер это поддерживает. Звук определяет ОС.

## Проверки

Окончательный прогон 6 октября 2026:

- Backend: **223 теста прошли**, PostgreSQL обязателен; покрытие с учётом ветвлений **92,42%**.
- Ruff, форматирование Python и strict mypy (36 файлов) прошли.
- Frontend: **21 Vitest**, TypeScript, ESLint, Prettier и production build прошли.
- **7 Playwright-сценариев прошли в Windows Edge за 20,8 секунды**: два клиента,
  аварийное подтверждение, открытая карточка, reconnect, нативный service worker,
  прежние сценарии фото/материалов/offline/ролей/отзыва сессии.
- Выдача появилась у исполнителя за **2409 мс**, принятие в открытой карточке мастера —
  за **1412 мс**. Это отдельный локальный замер, не SLA мобильной сети.
- Push-событие инъецировано через Chrome DevTools Protocol в отдельный браузерный процесс;
  настоящая Notification зарегистрирована с requireInteraction и ожидаемой ссылкой.
- Миграция/откат в изолированной схеме, ORM parity, основная миграция и uv build прошли.
- Независимый verifier: **PASS**, отдельно 89 серверных и 21 frontend-тест, lint/types/build.
- Скриншоты журнала на 390px и открытой карточки мастера на 1440px просмотрены root.

Основная база сохранила 600 нарядов, 4059 событий, 1200 записей материалов, 570 оценок,
19 сотрудников и 72 допуска. Миграция теперь 0003_notifications.
Локальная PWA: localhost:5173; API: localhost:8000; worker запущен отдельно.
Контакт VAPID получен из GitHub origin, приватный ключ лежит в var/webpush/vapid_private.pem.
Полная команда повторения браузерной проверки и изоляция БД описаны в этапе 4;
helper теперь также запускает worker без внешней отправки push.

Физические Android/iOS и реальная доставка через push-провайдера пока не подтверждены.
Браузерная инъекция push-события проверяет обработчик/нативную Notification, но не сеть
провайдера и не поведение ОС телефона. R15 остаётся частично закрытым до этапа 8.
Docker/production HTTPS и удалённый GitHub Actions также не являются проверками этого этапа.
