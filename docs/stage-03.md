# Этап 3 — наряды, история, материалы и фотографии

Дата проверки: 5 октября 2026. База этапа: пользовательский коммит `87f738b`.
Предлагаемый коммит: `feat: implement work-order workflow and repair evidence`.
Staging/commit/push выполняет пользователь.

## Реализовано

- Выдача с серверным номером/временем и проверкой участка, оборудования, исполнителя и смены.
- Принятие, очередь, отказ, старт, пауза, возобновление, сдача; причины и запрещённые переходы.
- Переназначение, отмена, приоритет, комментарии, возврат и закрытие мастером по актуальной проверке.
- У исполнителя максимум одна работа `in_progress`; конкурентный второй старт получает 409.
- Список/фильтры/счётчики, карточка, история оборудования, события с курсором и загрузка сотрудников.
- Материалы с положительным Decimal до трёх знаков; нулевой расход требует объяснения.
- Фото до/после: приватная загрузка/выдача, очистка метаданных, проверка и сжатие.
- `expected_version`, идемпотентность, неизменяемый через UPDATE/DELETE аудит и outbox.
- Попытки ремонта и версии сдач: старая оценка не относится к новому результату.

Это серверный этап. PWA — этап 4, доставка/worker — 5, реальные правила/LLM/vision — 6.
Синтетические оценки seed и тестовые вызовы сервиса оценки не выдаются за подключённый ИИ.

## HTTP-контракт для следующего этапа

Префикс `/api/v1`, Bearer-токен из `/auth/login`. UUID справочников берутся из `/catalog`,
назначения — из `/catalog/employees` и `/workload`. Точные схемы находятся в `/docs` и `/openapi.json`.

| Команда | Поля помимо `action` и `expected_version` |
| --- | --- |
| `accept`, `queue`, `start`, `resume`, `close` | Нет |
| `reject`, `pause`, `cancel`, `override_close`, `request_rework` | `reason` (3–1000 символов) |
| `reassign` | `reason`, `executor_id` |
| `change_priority` | `reason`, `priority` |
| `comment` | `comment` |
| `complete` | `completion` |

Лишние поля запрещены. Нельзя отправить `status` или системные действия ИИ.
Команды, допустимые для роли, дополнительно ограничены текущим состоянием домена.
`close` требует положительной актуальной проверки без флага ручного пересмотра;
`override_close` сохраняет причину решения мастера. У внутреннего `apply_review` нет HTTP-маршрута.

Создание `POST /work-orders` (вместо placeholders — реальные UUID и будущий срок):

```json
{
  "work_type": "unplanned",
  "description": "Проверить утечку масла в гидросистеме",
  "area_id": "<UUID участка>",
  "equipment_id": "<UUID оборудования>",
  "executor_id": "<UUID исполнителя>",
  "priority": "high",
  "deadline": "2026-10-06T18:00:00+05:00"
}
```

Сдача `POST /work-orders/{id}/actions`:

```json
{
  "action": "complete",
  "expected_version": 4,
  "completion": {
    "work_description": "Заменено уплотнение, соединение проверено под давлением",
    "fault_code_id": "<UUID шифра>",
    "materials": [{"material_id": "<UUID материала>", "quantity": "0.125"}],
    "comment": "Утечка при контрольном запуске не обнаружена"
  }
}
```

Если материалов нет, передаются `materials: []` и непустой `no_materials_reason`.
Каждая следующая сдача фиксирует **дополнительный** расход своей попытки;
прошлое списание сохраняется. История сдачи хранит снимок текста, шифра, материалов и комментария.

Каждый POST требует уникальный для нового намерения `Idempotency-Key` (8–128 ASCII-символов:
буквы, цифры, `.`, `_`, `:`, `-`). Ключ принадлежит автору; проверяются ресурс, операция и payload.
Повтор с прежним ключом и тем же телом возвращает исходный результат без второго события,
списания или файла, даже если состояние уже изменилось. Другое тело/другой наряд с тем же
ключом — 409. Повтор не отменяет проверки текущей видимости объекта.
У действия/фото `expected_version` должен соответствовать текущей карточке; после любого
изменения, включая комментарий и фото, версия возрастает. После 409 UI перечитывает карточку.

Список поддерживает повторяемый `status`, `area_id`, `equipment_id`, `executor_id`,
`priority`, `work_type`, `overdue`, `offset`, `limit` (1–200).
`counts` содержит все статусы в выбранных фильтрах, включая нулевые;
порядок: аварийный приоритет первым, затем срок и UUID. Просрочка — вычисляемый признак.
История `/events?after_sequence=N&limit=100` возвращает `next_after`.

## Права и занятость

| Роль | Чтение | Изменение |
| --- | --- | --- |
| Мастер | Наряды, фото, оборудование и загрузка доступных участков | Выдача; управление только своими нарядами |
| Исполнитель | Свои назначения, их фото и события; собственная загрузка | Действия исполнителя и фото после |
| Руководитель | Наряды, фото, история и загрузка доступных участков | Нет команд ремонта |
| Администратор | Справочники и доступ сотрудников | Справочники/учётки; не команды ремонта |

Идентификатор чужого наряда/фото даёт 404. Переназначение лишает прежнего исполнителя доступа.
Занятость выводится из актуальных данных; пауза освобождает человека для другой работы.
Если он занят за пределами доступного мастеру участка, API показывает занятость без номера/ID чужого наряда.
Сменность меняется существующим admin-маршрутом доступа через `is_on_shift`;
снять со смены при `in_progress` нельзя. Изменение доступа отзывает сессии, как на этапе 2.

## Фотографии

`POST /work-orders/{id}/photos?kind=before&expected_version=1`:
сырые байты файла в теле, `Content-Type` — `image/jpeg`, `image/png` или `image/webp`.
Это не multipart и не base64 JSON. `captured_at` необязателен: ISO-время с timezone;
сервер допускает старое время как недоверенное заявление, но отвергает более 5 минут в будущем.

Фото до добавляет выдавший мастер, пока наряд `issued` (до 5 на наряд).
Фото после добавляет назначенный исполнитель в `in_progress`/`paused` (до 5 на попытку).
При сдаче с фотографиями сначала загрузите их, затем используйте версию последней загрузки.

По умолчанию: вход до 10 MiB/24 млн пикселей, выход JPEG до 2 MiB/2048 px по большей стороне.
MIME сверяется с декодированным форматом; повреждённые и анимированные изображения отклоняются.
Поворот применяется до удаления EXIF/геометок, прозрачность сводится на белый фон.
Сохраняются SHA-256 нормализованного JPEG, автор, серверное время, попытка и размер.
Пути файлов не выдаются клиенту. Файлы имеют права 600, каталог — 700; symlink запрещены.
GET фотографии требует тех же прав на наряд и возвращает `Cache-Control: no-store`/`nosniff`.
Ошибки размера — 413, формата MIME — 415, содержимого — 422, лимита количества/версии — 409.

Файл и БД не образуют общую файловую транзакцию. Обработанная ошибка БД удаляет новый файл
(проверено внедрением сбоя); аварийное завершение процесса до commit может оставить закрытый
файл без ссылки. Для пилота нужны сверка volume с БД, очистка таких файлов и совместные backup.
Дубликаты по смыслу/свежесть/качество изображения будут проверяться на этапе 6.
Мобильная загрузка за 10 секунд пока не измерена.

## Транзакции и миграция

Миграция `0002_order_workflow` добавляет outbox/идемпотентность, версии событий/сдач,
номер попытки, уникальность текущей работы и запрет изменения событий триггером.
Исторические события сохраняются с nullable-версией; ранее завершённые наряды получают
`last_submission_version` из текущей версии. Существующие данные не пересоздаются.

```bash
uv sync --locked
uv run --locked alembic upgrade head
uv run --locked alembic check
```

Наряд блокируется `FOR UPDATE`; команда, материалы, событие, outbox и ответ для повторов
сохраняются атомарно. Назначение/старт сериализуются блокировкой сотрудника.
Уникальный частичный индекс БД дополнительно защищает от двух активных работ.
Все соединения приложения используют UTC. Список с подсчётами и карточка читаются
в согласованном snapshot `REPEATABLE READ READ ONLY`.

Outbox содержит факт изменения и идентификаторы без полного содержимого наряда.
Пока нет доставщика: наличие строки outbox не означает отправленное уведомление.

## Граница готовности

Новый наряд после сдачи остаётся `completed`, пока проверку не обработает будущий worker.
Кейс разрешает показать дефектную сдачу без фото: сервер принимает доказательства как есть,
но не объявляет ремонт качественным и не закрывает его автоматически.
Внутренний сервис уже умеет сохранить проверку и обеспечить решение мастера;
реальное получение вердикта, проверка обязательных фото и отчёт появятся на этапе 6.

Нет мобильного интерфейса, WebSocket, push, таймеров, внешнего ИИ, аналитики и промышленного
развёртывания. Docker-альтернатива и удалённый GitHub Actions не запускались.
Следующий отдельный этап — русская PWA исполнителя и панель мастера.
