# Этап 4 — русская PWA и рабочее место мастера

База этапа: пользовательский коммит `0bfad38`.
Предлагаемый коммит: `feat: build mobile work-order app and supervisor dashboard`.
Staging, commit и push выполняет пользователь.

## Запуск в Ubuntu / WSL

API и PostgreSQL запускаются командами из основного README на `127.0.0.1:8000`.
Для интерфейса откройте второй терминал в корне проекта:

```bash
uv run --locked python scripts/dev_frontend.py bootstrap
bash scripts/frontend.sh ci
bash scripts/frontend.sh run dev -- --host 127.0.0.1 --port 5173
```

Откройте `http://localhost:5173`. Используются существующие демо-учётки и локальный секрет
из `var/demo-credentials.txt`; пароли в клиентский bundle не добавляются.
Установщик помещает закреплённый Node 24.21.0 в игнорируемый `var/node`, проверяет SHA-256
официального архива и не меняет системный Node. Для своей установки Node нужна версия `.node-version`.
Зависимости интерфейса закреплены в `frontend/package-lock.json`.

Проверка собранной PWA, включая service worker:

```bash
bash scripts/frontend.sh run build
bash scripts/frontend.sh run preview -- --host 127.0.0.1 --port 5173
```

Dev и preview используют один порт: запускайте один из них.
Vite проксирует `/api` к `127.0.0.1:8000`. Для отдельного API задаётся серверная переменная
`NARYADAI_API_TARGET`; DSN, пароли и токены не должны попадать в `VITE_*`.
Preview предназначен для локальной проверки сборки; промышленный HTTPS — этап 8.
На реальном телефоне `localhost` указывает на сам телефон, поэтому мобильное развёртывание
и установку нужно отдельно проверить через HTTPS. Эмуляция ширины/касания этого не заменяет.

## Контракт данных и работа без связи

Единственный источник подтверждённых статусов — API. Кнопки ограничены ролью, владельцем
наряда и его состоянием; сервер повторно проверяет все права и переходы.
Время ремонта отображается в часовом поясе предприятия `Asia/Almaty`.

Ключ сессии и срок хранятся в `sessionStorage`; пароль не сохраняется. Вход требует связи.
Офлайн-данные находятся в IndexedDB отдельно для каждого сотрудника и имеют срок жизни 8 часов.
Сохранённый снимок помечается временем получения и не объявляется актуальными данными сервера.

Очередь предназначена для действий исполнителя. На один наряд допускается одно ожидающее
действие, чтобы следующие команды не строились на неподтверждённой версии.
Действие сохраняется **до первого запроса**; ключ, тело и `expected_version` не меняются
при повторе. Поэтому потеря ответа после серверного commit не приводит ко второму списанию.

- Успешный ответ удаляет команду из очереди и запускает обновление карточки.
- Сетевой сбой/5xx/429 оставляет команду для последующего повтора.
- 409 и другие постоянные отказы блокируют автоматические повторы: пользователь проверяет
  карточку, удаляет устаревшее намерение и формирует новое. Версия автоматически не подменяется.
- 401 прекращает отправку и возвращает ко входу.
- Выход удаляет локальные снимки и ожидающие действия текущего сотрудника.

Выдача наряда мастером и загрузка фото требуют связи; файлы не складываются в офлайн-очередь.
Service worker сохраняет только публичную оболочку приложения. Ответы API, авторизация и
фотографии не помещаются в Cache Storage. Приватные фото показываются через авторизованный
запрос и временный blob URL.

## Браузерная проверка с отдельной БД

Основная демобаза не используется для E2E. Helper требует PostgreSQL с суффиксом `_test`,
создаёт уникальную схему, мигрирует и заполняет её. После SIGTERM/Ctrl+C удаляются только
эта схема, её фото и приватный файл состояния. `var/postgres/test-url` создаёт DB-helper;
в другой среде задайте `NARYADAI_TEST_DATABASE_URL`.

```bash
uv run --locked python scripts/frontend_test_server.py --port 58001 --state-file tmp/e2e-server.json
```

В другом терминале соберите интерфейс и запустите preview:

```bash
bash scripts/frontend.sh run build
NARYADAI_API_TARGET=http://127.0.0.1:58001 bash scripts/frontend.sh run preview -- --host 127.0.0.1 --port 5173
```

Браузерные тесты находятся в `frontend/e2e`, конфигурация — `frontend/playwright.config.ts`.
Windows-проверка использует установленный Edge, Linux — доступный Playwright Chromium
или явно заданный `NARYADAI_BROWSER_CHANNEL`. Наличие браузера нужно проверить отдельно.
Локальный JSON `tmp/e2e-server.json` содержит временный секрет, имеет права 600 и не попадает в Git.
Скриншоты из `frontend/test-results` также игнорируются; они не являются фотографиями реального ремонта.


В третьем терминале Ubuntu, если Playwright Chromium уже установлен:

```bash
bash scripts/frontend.sh exec -- playwright test
```

Если браузера нет, установите его командой `bash scripts/frontend.sh exec -- playwright install chromium`
(загрузка браузера и системные библиотеки проверяются отдельно). В данной среде использован
уже установленный Windows Edge; команда из PowerShell в корне проекта:

```powershell
node frontend/node_modules/@playwright/test/cli.js test --config frontend/playwright.config.ts
```

Сценарий использует настоящий API и PostgreSQL: выдача мастером, мобильные действия,
приватное фото, две строки расхода, повтор после офлайн-перезагрузки, конфликт версии,
роли, клавиатура, отзыв сессии и очистка данных. PNG fixture создан программно и явно
помечен как тестовый; он не подтверждает качество реального ремонта.

## Что остаётся следующим этапам

Нет WebSocket, push, фоновых таймеров и реального провайдера ИИ. Сданный новый наряд ожидает
проверки; исторические оценки seed явно синтетические. Статистика, отчёты и редактор всех
справочников в UI не входят в эту часть; admin API предыдущего этапа остаётся доступным.

Реальные замеры выдачи ≤60 секунд/≤6 нажатий и загрузки фото ≤10 секунд на мобильной сети,
установка Android/iOS, HTTPS и репетиция на 2–3 устройствах требуют этапа 8.
Не следует выводить готовность этих критериев только из автоматических браузерных тестов.
