# Уведомления и ввод текста

Журнал объединяет уведомления по `order_id`, а сообщения о поломках — по
`fault_report_id`. Внутри блока остаются отдельные события, время, отметка прочтения
и подтверждение срочного сообщения. Открытие наряда и подтверждение получения
не заменяют принятие наряда исполнителем.

Группировка действует в пределах загруженной страницы (50 событий). Счётчик
страницы показывает количество событий, а не количество нарядов. После прочтения
список обновляется с сервера; пустая последняя страница возвращает к предыдущей.
Если номер отсутствует в payload и тексте, интерфейс не придумывает его.

Web Push использует заголовок и текст конкретного события. Длинные уведомления
о просрочке и эскалации имеют отдельный короткий вариант для устройства; полный
контекст сохраняется в журнале. Ограничения транспорта: 120 символов заголовка,
240 символов описания. Права получателя проверяются повторно перед отправкой.
Для применения серверных изменений нужно перезапустить API и worker; миграции
и повторное заполнение базы не нужны.

На фронтенде `lib/inputText.ts` убирает только крайние пробелы из полей, вводимых
человеком: логинов, названий, описаний, причин, комментариев и вопросов. Серверная
валидация остаётся обязательной. Пробелы внутри текста, пароли, идентификаторы,
ключи push и файлы не изменяются. Нормализация предшествует расчёту ключа повторной
попытки запроса: добавление случайных крайних пробелов не создаёт новый наряд
после потери сетевого ответа.

Проверки:

- `frontend/e2e/notifications.spec.ts`: группировка, подтверждение, непрочитанные,
  ошибка и повторная загрузка, последняя страница, переход в наряд; 390/700/1440 px.
- `frontend/e2e/realtime.spec.ts`: два клиента и service worker. Проверка service
  worker требует production-сборки (`vite preview`), в dev-режиме он не включён.
- `frontend/e2e/fault-reports.spec.ts`: закрытие сообщения с причиной; раскрытие
  формы больше не очищает введённую причину отложенным событием `toggle`.
- `tests/integration/test_notification_engine.py`, `test_push_delivery.py`,
  `test_notifications_api.py`: создание, доставка, повторные попытки и права.
- `tests/unit/test_input_whitespace.py`, `frontend/src/lib/inputText.test.ts` и
  проверки API: очистка текста и сохранение точного значения пароля.

Браузерная эмуляция проверяет адаптивную вёрстку; доставка через APNs/FCM на
физическое устройство проверяется отдельно.

## Частота и прекращение повторов

- Выдача, переназначение и изменения статуса: по событию, без искусственной задержки.
- Напоминание исполнителю до срока: однократно за 30 минут до срока (при более
  поздней выдаче — при первой проверке до срока).
- Наряд не принят: один сигнал мастеру через 10 минут, для аварийного — через
  3 минуты. Это порог первого сигнала, а не период повторения.
- Просрочка: первый сигнал мастеру и исполнителю при обнаружении, затем не раньше
  чем через 120 минут **от предыдущего фактически созданного уведомления**.
  Максимум три уведомления каждому: первое и два повтора. Простое чтение не
  снимает незавершённую работу; «Подтвердить получение» останавливает повторы
  для конкретного получателя и данного срока/попытки наряда.
- Руководитель получает одну эскалацию через 60 минут просрочки, без повторной
  рассылки каждые полчаса.
- Новый срок или новая попытка выполнения образует отдельный цикл. Старые
  уведомления остаются в журнале; уже накопленные повторы учитываются в лимите.
- Частота относится к одному наряду и получателю. Новые события по другим
  нарядам по-прежнему могут приходить сразу.

`NARYADAI_OVERDUE_REPEAT_MINUTES` задаёт интервал повторов (по умолчанию 120,
минимум 30 минут). Изменение настроек требует перезапуска worker; для Docker
после изменения кода нужно пересобрать образ API/worker. Миграции и повторный сид
для этой настройки не нужны.

Перед отправкой на телефон напоминание дополнительно сверяется с текущим
нарядом. Прочитанные/подтверждённые, заменённые более свежим напоминанием,
старше двух часов, относящиеся к старому сроку/попытке или уже решённой проблеме
не отправляются. Их записи в журнале сохраняются. Это ограничение касается
напоминаний, а не новых событий жизненного цикла наряда.
