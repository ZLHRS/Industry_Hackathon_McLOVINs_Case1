Python 3.13, проектный Node 24, Docker с Linux-контейнерами.

## Исправления переносимости

- Поиск стандартных установок PostgreSQL 16 на macOS, включая Homebrew на Intel
  и Apple Silicon. При нескольких версиях выбираются бинарники версии существующего кластера.
- Повторная остановка уже остановленного проектного PostgreSQL не считается ошибкой.
- Единый нативный запуск сообщает о неподдерживаемой ОС до запуска сервисов.
- Уточнены требования к файлу credentials постоянного туннеля и его правам.

Регрессионная проверка:

```bash
uv run --locked python -m pytest tests/unit/test_phone_tunnel.py tests/unit/test_docker_setup.py tests/unit/test_demo.py tests/unit/test_dev_runtime.py -q
```

Результат: **52 passed**. macOS Intel/ARM64 проверены анализом кода и тестами
выбора платформы, но не физическим запуском. Нативный Windows Python не является
поддерживаемым способом: на Windows выполняйте инструкции в Ubuntu/WSL.
Docker Desktop должен использовать Linux-контейнеры. Запуск Docker на ARM64
в этой проверке не выполнялся.

## Что подготовить на другом ноутбуке

1. Получить актуальный код и создать окружение по инструкции в README.
2. Не переносить готовые `.venv`, `node_modules` или каталог PostgreSQL между платформами.
3. Выбрать базу: нативный кластер и Docker volume независимы. Для новой базы
   применить миграции и сид; для существующих данных использовать резервную копию.
4. Для Docker сначала запустить Docker Engine/Desktop и выполнить `docker info`,
   затем `python3 scripts/docker_setup.py`. Только после этого запускать Compose.
5. Настроить приватные ключи нужного режима. Git их не переносит.
6. Проверить readiness по адресу именно выбранного запуска. Свободные порты,
   доступ в интернет и работающий DNS зависят от конкретного ноутбука и сети.

## Если домен отвечает 1033

Cloudflare не видит здорового подключения `cloudflared` к туннелю,
обслуживающему этот адрес ([официальное объяснение](https://developers.cloudflare.com/tunnel/troubleshooting/)).
Это не подтверждает неисправность локального API и не исправляется очисткой кэша PWA.

На **ноутбуке, обслуживающем домен**, выполните:

```bash
docker info
docker compose --env-file .env.docker -f compose.yaml -f compose.tunnel.yaml -f compose.ai.yaml ps --all
docker compose --env-file .env.docker -f compose.yaml -f compose.tunnel.yaml -f compose.ai.yaml logs --tail=60 tunnel
```

Проверьте, что ноутбук не спит, Docker работает, credentials-файл существует,
соответствует нужному туннелю и читается контейнером. После устранения причины
повторите команду запуска из README и проверку:

```bash
curl --fail --show-error --max-time 20 https://technaryad.online/api/v1/health/ready
```

Если внешний ИИ не настроен, уберите `-f compose.ai.yaml`. Не подключайте к тому же
постоянному туннелю второй ноутбук с отдельной базой для проверки: запросы могут
попасть в разные экземпляры приложения. Для локальной проверки достаточно базового Compose.
